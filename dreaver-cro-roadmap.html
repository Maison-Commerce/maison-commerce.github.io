T1CLPBriefed

Use-case filters above the product grid

A compact row of use-case filter chips directly above the grid — Wandelen, Hardlopen, Onder een bureau, Met helling, Extra ondersteuning — so browse-first shoppers can narrow seven models to the ones that fit their intent, without leaving for the keuzehulp or the comparison table.

KPIs
PDP CTR · Sessions Converted
Targeting
Loopbanden collection page
Segment
All traffic · mobile priority (~75%)
Tool
Experiment platform
Evidence
Model-selection uncertainty across all 3 surveys · ~70% comparing alternatives · ~10% comparing Dreaver's own models · ~75–77% mobile
A/B test ID
MC_CLP_USECASE_FILTERS_ABOVE_GRID_DREAVER · generated id MC_CLP_USECASEFILTERS

Problem

The page has a prominent keuzehulp for guided advice, but browse-first shoppers get only a sort control above the seven-product grid. To narrow by intended use they must interpret every model or scroll past the full grid to the comparison table — demanding on mobile, ~75% of the audience.

Solution

A compact, mobile-friendly row of filter chips immediately above the grid (Wandelen, Hardlopen, Onder een bureau, Met helling, Extra ondersteuning). Selecting a chip instantly narrows or reorders the existing cards; chips combine and clear easily. Complements the keuzehulp rather than replacing it.

Hypothesis

IF we add use-case filter chips directly above the product grid that instantly narrow the existing cards,

THEN collection→PDP click-through and CVR will increase,

BECAUSE model-selection uncertainty appears across all three surveys and ~70% of comparison-question respondents were comparing alternatives — letting intent-led shoppers self-filter reduces the interpretation load, especially for the ~75% mobile audience.

Decision-making product cards

Give every card a "Best voor" line and two or three decision facts — walking vs running, storage, noise, incline, support — plus a model-level rating, so shoppers can tell the models apart on the grid instead of interpreting specs.

MC_CLP_DECISION_MAKING_PRODUCT_CARDS_DREAVER · generated id MC_CLP_DECISIONCARDS

Problem

Cards show a positioning line, speed, incline where relevant, price and discount — but shoppers still have to work out which technical differences matter for their use. Decision criteria the surveys flagged (walking vs running, storage, noise, support) are missing from the card or buried further down.

Solution

Add a clear "Best voor" label and 2–3 meaningful decision facts to every card (walking-only vs walking + running, storage format, noise level, incline, support rail). Prioritise customer-facing differences over more specs, and add model-level review ratings where volume allows.

Hypothesis

IF we turn each product card into a decision card with a "Best voor" line, 2–3 customer-facing facts and a model rating,

THEN collection→PDP click-through and CVR will rise,

BECAUSE customers repeatedly struggle to choose between models, and the exact criteria they ask for — fit/storage (10.5% top objection) and noise (22%) — are the ones missing from the card, so surfacing them lets shoppers self-select the right model faster.

T3CLPBriefed

Mobile-first model comparison

Rebuild the existing comparison table around choice: pick 2–3 models, keep names, images and current prices pinned while scrolling, lead with "Best voor" / walking-running / storage before the specs, and fix the promo-price mismatch.

Segment

Tool

Evidence

A/B test ID
MC_CLP_MOBILE_COMPARISON_EXPERIENCE_DREAVER · generated id MC_CLP_MOBILECOMPARE

Problem

The page already has a comprehensive comparison table, so a second spec table would duplicate content — the opportunity is to fix this one. Today it sits after all seven cards, is spec-led, shows only two models on mobile with the rest behind "Toon meer," and doesn't explain how to compare. Elevate Pro also shows €429 on the card but €529 in the table, with the regular price not clearly labelled.

Solution

Let visitors select 2–3 models to compare. Lead with "Best voor," walking/running suitability and storage before detailed specs; keep model names, images and current prices sticky while scrolling; add a clear mobile swipe/select control; show promo prices consistently and label regular prices; link to it from a visible "Vergelijk modellen" action above the grid; keep technical rows for those who want them.

Hypothesis

IF we rebuild the comparison around model selection — sticky headers, choice-led rows first, consistent pricing and a swipe control —

THEN comparison engagement and CVR will rise,

BECAUSE internal model confusion appears across all three surveys and customers explicitly asked for side-by-side comparison, yet the current mobile experience (2 models, spec-led, "Toon meer") makes that hard for the ~75% mobile audience.

MC_CLP_DREAVER_VS_ALTERNATIVES_DREAVER · generated id MC_CLP_VSALTERNATIVES

Problem

The page helps compare Dreaver models but says nothing about competing brands or cheap marketplace treadmills — so shoppers leave the site to finish that part of their research.

Solution

After the Dreaver model comparison, add a three-column comparison — Dreaver / premium online alternative / budget marketplace — across criteria like Dutch service, warranty & repair, app/training, incline, walking + running, verified reviews and post-purchase support. Run a competitor audit first; every claim must be current, factual and supportable; use neutral language ("varieert per verkoper") where quality varies.

Hypothesis

IF we add a factual Dreaver-vs-alternatives comparison after the model table,

THEN CVR will rise,

BECAUSE ~70% of comparison-question respondents were comparing alternatives (Moov = 74% of named competitors, plus budget bol.com options), and trust, Dutch credentials, service and warranty are what tip shoppers to Dreaver — keeping that comparison on-site removes a research detour.

Problem

IF we add a focused proof module framing movement as something that lasts, backed by the six-month usage figure, between the hero and grid,

THEN CVR will rise,

BECAUSE price was the top exit factor (41.7%) and usage doubt affected 28.3% of exit respondents — proof that owners keep using it de-risks both objections before the click into a PDP.

Problem

The PDP says it fits under a desk, lists dimensions inside the specs, and has a compact-storage section lower down — but none gives an immediate, measurable answer to whether it fits under this shopper's couch, desk or chosen spot. Execution

Recommended order

Ten tests across two surfaces, sequenced by the research prioritisation. Run tests sequentially within each surface — tests that touch the same area confound each other if run at once — while the two surfaces can run as parallel tracks.

Settle before shipping CLP tests

Choice-led rows + consistent promo pricing for T3, use-case tag mapping for T1, "Best voor" copy + facts + ratings for T2, validated proof figures & owner imagery for T5, and a competitor audit for T4.

Top CLP priority: improves an existing feature and resolves the €429/€529 price mismatch. Ship it on its own.

Collection · Phase 2

T1 · T2 — help shoppers self-select

Filters and decision cards both act on the grid above the fold; run separately as they share the same area.

Collection · Phase 3

T5 · T4 — de-risk value & brand choice

Value proof first; the alternatives comparison (T4) ships last, only after the competitor audit clears every claim.

Product (Elevate Pro) · Phase 0 — Prerequisites

Verify the six-month 88% claim — source, sample, definition — for T9; complete a competitor audit for T7; confirm exact in-use, folded and upright dimensions for T8; confirm PostNL/DPD carrier rules; confirm the noise level under defined test conditions for T10; write the need-based selector copy + mini table for T6.

Highest PDP priority: substantiate the usage claim and add the first-14-days plan. It answers the largest emotional objection — usage doubt (28.3% of exit respondents).

Product · Phase 2

The value comparison (T7, after audit) and the fit/storage modal (T8) both add content near the buy box — run them sequentially, not together. T7 carries the "Needs audit" status until its claims are verified.
